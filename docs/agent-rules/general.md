# 通用协作与编码细则

## 业务目的
沉淀可跨项目复用的协作、分析、编码、测试、文档维护与类型检查原则；作为 [AGENTS.md](../../AGENTS.md) 中“通用规则”的展开说明。

## 适用边界
- 本文负责展开通用协作规则；`AGENTS.md` 只保留必须立即生效的高频摘要。
- 若本文与项目专题文档冲突，优先以接口文档、业务文档、抓包、日志与项目专题文档中的明确事实为准。
- 若项目存在专项 skill、专题文档或额外流程约定，在遵守本文前提下，继续遵守对应规则。
- 项目级文档协作约定与项目内 skills 使用约定，统一以 [AGENTS.md](../../AGENTS.md) 为准，本文不重复维护全文。

## 协作与结论表达
- 默认使用中文回复；代码注释与代码示例使用中文。
- 对“我生成的代码 / 我引入的测试 / 我给出的设计”负责；出现问题时先自查代码与事实依据，禁止把责任推给开发者。
- 当用户指出错误时，必须明确承认，并给出可验证的修正方案，说明涉及文件、关键逻辑，以及复现或验证方式。
- 结论必须区分“事实/证据”和“推断/猜测”；没有抓包、日志、代码或文档依据时，先提澄清问题，不得以主观判断下结论。
- 禁止把“避免误删”的一般性警惕，偷换成“未核实前先保留”的默认结论；对可重建的派生产物和临时目录，默认动作应是先核实归属、状态与复用价值，而不是先保留再让用户收尾。
- 对目录、产物、实验记录是否要保留或清理的判断，同样必须基于事实证据；禁止用“可能还有别的内容”“也许后面会用到”这类未经核实的推断阻止清理已确认无价值的脏数据。

## 分析与方案输出
- 先读接口说明、业务逻辑、现有实现，再动手写代码；不允许凭经验猜接口行为。
- 先明确用户当前要解决的直接问题与必答点；输出时优先回答这些问题，再补背景、分类或范式讨论。
- 当需要判断外部接口数据口径是否一致时，优先自行阅读文档并做最小实测验证，给出可复现证据与结论；不得把分析工作转交给开发者。
- 方案与选项输出遵守帕累托/支配关系：若方案 A 在所有关键维度上都不优于方案 B，且至少一维更差，则 A 默认不应列为备选。
- 如确需保留非 dominant 方案，必须在同一段内写清保留原因、适用边界，以及它为何仍可能是该场景的最优选择。
- 若项目要求在方案阶段同步产出 Issue、任务单或设计稿，内容至少覆盖：背景、目标、范围边界、接口依据、任务拆分、验收标准、风险，以及需要用户确认的问题。

## 编码原则
- 修复 bug 时必须定位根因，写清因果逻辑，禁止“绕过去”。
- 代码结构必须直线化、可读性优先；避免过度抽象、过深嵌套与复杂控制流。
- 禁止为了“更鲁棒”而添加冗余兜底逻辑，例如多层 `try-catch`、重复 `null/空` 判断、吞错。
- 只在有明确需求或明确边界条件时才加校验；没有依据就不要添加。
- 涉及第三方 SDK、数据库驱动、消息队列客户端等有状态依赖时，必须先区分并证明“认证态 / 连接态 / 并发态 / 缓存态”的生命周期，再修改资源管理逻辑；禁止在未证明副作用前，用 `reset`、重建 client、强制重连等方式直接压连接数或压资源占用。
- 若某个资源治理改动会改变“是否复用已认证会话 / 是否触发重新登录 / 是否改变上游风控行为”，该改动按行为变更处理；必须先有源码、官方文档、抓包或最小实测依据，才能实现。
- 优先使用现代语法糖和简洁逻辑；除非逻辑确实复杂，否则不要添加兜底逻辑。
- 只在业务意图不自明、边界条件复杂或外部约束强时补充注释；注释优先解释“为什么”，不要逐行重复“做了什么”。
- 若包含 `main` 方法，需要补充清晰的示例运行指令。
- 文档或模块注释中的标题直接写 `业务目的`，不要写成“业务目的（一句话）”。

## 测试与验证
- 新增或调整测试时，默认优先真实集成测试，不默认使用 mock；只有用户明确要求时才使用 mock。
- 集成测试输入优先复用上游真实任务产物；不要在测试里手工插入上游 domain 数据。
- 若集成测试所需前置数据不存在，直接 `skip`，并在测试说明或输出中写清所缺前置数据以及生成方式。
- 数据任务默认优先“简单、可验证的全量实现”；只有观测到真实瓶颈后，再引入分片、并行、流水线等复杂优化。

## 安全与输出约束
- 禁止在回复、日志、命令输出中展示敏感信息，包括但不限于 `.env` 全文、DSN 密码、AccessToken、API Key、Cookie、私有仓库 Token。
- 排障时只允许输出“变量名 + 是否已配置 / 长度 / 末尾少量掩码”。
- 禁止执行会覆盖、删除工作区内容的操作，例如 `git restore .`、`git reset --hard`、`git clean -fd`。

## 静态类型检查与 Python 约定
- 新增或修改代码时，默认不引入 Pylance/Pyright 的红色报错，尤其避免 `reportGeneralTypeIssues`。
- 对第三方库类型缺失或不完整导致的误报，优先使用最小范围的类型标注、`cast()` 或标准库封装修正；最后才使用 ignore，并在同一行写清具体原因与范围边界。
- DB-API 连接或游标场景，不要写 `with conn.cursor() as cur:`；更推荐：

```python
from contextlib import closing

with closing(conn.cursor()) as cur:
    cur.execute("SELECT 1")
```

- 若需要更细粒度控制游标生命周期，可以显式使用 `try/finally` 关闭，而不是为了消红大面积添加 `# type: ignore` 或 `# pyright: ignore`。

## 输出前自检清单
- 我是否引用了接口文档、抓包结果、日志或业务规则的明确依据？
- 我是否先回答了用户的直接问题，而不是先展开抽象范式？
- 我是否能用更少的分支、更少的防御代码完成同样逻辑？
- 我是否避免了无根据的兜底与兜错？
- 我是否只改动了与需求直接相关的部分？
- 我是否遵守了真实集成测试优先、上游产物复用优先的测试原则？
- 我是否同步更新了必要的文档说明、索引或入口？
- 我是否能用一句话解释本次修改的业务目的？
